## Prospective successful-export client repair

Final Spec review of `831c4bb` found that successful raw downloads checked response
generation only on errors. A coherent copied manifest can remain at generation A
while a confirmed prune advances the response header to B. With SSE held, accepting
that result would bypass current-snapshot recovery.

Test `90418f2` exposed the real native race; client fix
`74e0187db1c19ff50f5b564ae49ab829fe65a08d` checks the generation header before
success/error parsing, cancels the stale response, obtains the existing settings
snapshot, and rejects that operation for explicit retry. The guard also works when
ApiClient is already at B. Draft content/cutoff remain intact, stale prepared
confirmation is invalidated, and explicit retry downloads coherent B.

A separately owned qualified dependency copy, without another install, supplied
this repair's own production build `xbj9fOu1kF9q4vKyZx-z9` with 453 compiled files.
The authoritative 113 base shipping inputs were matched before changes; an initial

copy was preserved before the sole changed client build. Original measured source,
dependencies, build, fixture, and quiet-campaign proofs remained unchanged.
