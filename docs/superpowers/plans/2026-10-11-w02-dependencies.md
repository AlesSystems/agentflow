## Invariants and resolved choices

1. Preserve migrations 0000–0006 byte-for-byte. Add migration 0007 with dependency rows, policy defaults false, rework round default 0, immutable artifact/decision evidence, and nullable captured run evidence fields. Map SQLite policy integers explicitly to strict response booleans. Update explicit run projections and schema parity tests.
2. Dependencies have at most 20 direct, canonical UUID prerequisites. Atomically replace the whole set after expectedVersion, same-project, existence, archive, duplicate, self, no-active-attempt, and resulting full DAG checks. SQLite immediate transactions serialize competing edge changes. Never derive prerequisites from parents or reported workflow edges.
3. Readiness means each direct prerequisite has current human completion matching its current work revision. Return current and accepted revisions, prerequisite IDs, and bounded reasons. An empty set is ready. Reopen and work revision changes invalidate readiness immediately. Metadata-only edits preserve acceptance. Recheck readiness within the existing registration transaction only for a new implementation attempt, and within human completion. Reject registration with `409 dependencies_not_ready`. Existing attempts and review/verification reporting retain their lifecycle rules. Manual moves stay available.
4. Human-only commands remain protected both at the route and store boundary before receipt lookup. Exact authenticated command retries return original receipts before mutable state checks. Immutable run-ID registration retries and event-ID retries retain their earlier resolution order. Failed commands write no receipts, changes, projection, or history.
5. Keep the existing implementation registration bump of workRevision. New implementation, changed work text, reopen, and rework invalidate current artifact applicability while retaining old evidence. Round advances only on explicit rework. Rework requires Review, no active attempt, expectedVersion, and bounded reason, then returns Backlog and advances revision and round exactly once.
6. An artifact is an opaque nonempty reference of at most 2000 characters, with optional bounded display URL rendered as escaped inert text, never as a clickable link. Never fetch, inspect, or execute it. Implementation success may publish a reference on its captured current revision. Browser artifact publication can supply missing current evidence for manual work or current successful implementation work. Repeating the same current reference does not advance workRevision. Replacing an applicable reference advances workRevision once, preserves round and historical evidence, and rejects active attempts. It cannot make an old successful implementation satisfy the foundation's current-revision completion rule. Tasks with implementation history then need a successful current implementation attempt before acceptance.
7. Add an optional all-or-none evidence tuple to review/verification registration. If the relevant policy is required, require a current tuple/reference. Optional legacy review/verification registration and success without a decision remain execution evidence. An explicit approval or changes_requested decision always requires a captured matching tuple and bounded note, even for optional gates. Reject stale tuples or inappropriate purposes atomically. Store captures authoritatively instead of trusting caller claims.
8. A gate success under its enabled relevant policy requires explicit `approved` or `changes_requested` plus bounded evidence note. For disabled policies, old `{summary, evidenceUrl?}` successes remain valid. Failed, interrupted, cancelled, planning, or implementation attempts cannot imply approval. Reports never imply human acceptance. A tuple-current negative decision from either required gate stays blocking even if another same-tuple run approves later. New revision or explicit rework plus fresh approvals is the recovery path. Optional negative decisions display without enforcing their gate.
9. Completion retains Review, no-active, version, project, latest immutable implementation order, successful current revision, and human-only foundation checks. Add readiness and required current-tuple approval checks. No policy edit, task/parent status, workflow success, PR merge, or report completes a task automatically. Policy enabling can require valid existing current evidence but never retarget obsolete evidence.
10. Current readiness/evidence is a bounded projection separate from historical reports. Task reads include policy, round, current artifact, and current gate summaries. Historical artifacts and decisions stay accessible in bounded pages, using the existing task run/event history where sufficient and a small task-evidence read only for facts not represented there. Do not embed an unbounded history in every task or board response.
